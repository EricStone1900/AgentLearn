# 第四章 智能体经典范式完整学习实现流程

本文是《第四章 智能体经典范式构建》的 Node.js + TypeScript 完整实践总结，适合作为后续教学讲义和学习者复现手册。

配套工程：

```text
chapter4/agent-patterns-ts
```

学习者应按本文顺序完成，每一阶段都要经历以下四个环节：

1. 明确这一步要解决的问题。
2. 编写当前步骤的代码。
3. 理解代码在整个 Agent 数据流中的位置。
4. 运行类型检查或测试，确认当前步骤正确后再继续。

---

## 一、本章学习目标

完成本章后，学习者应该能够：

- 用 TypeScript 封装统一的 LLM 调用客户端。
- 理解 `API Key`、`Model ID`、`Base URL` 和超时配置的作用。
- 理解 Zod 为什么要在运行时验证外部数据。
- 实现可注册、可描述、可校验参数的工具系统。
- 实现 ReAct 的“思考 → 行动 → 观察”循环。
- 实现 Plan-and-Solve 的“先规划 → 后执行”流程。
- 实现 Reflection 的“初稿 → 反思 → 优化”循环。
- 用 Fake LLM 编写稳定、无网络、无 API 费用的单元测试。
- 根据任务特点选择合适的 Agent 范式。

---

## 二、完整学习路线

```text
工程搭建
  ↓
环境变量与 Zod 配置校验
  ↓
统一 LlmClient 接口
  ↓
OpenAI 兼容客户端与流式输出
  ↓
通用 JSON 解析器
  ↓
工具协议、注册表、计算器、搜索
  ↓
ReAct
  ↓
Plan-and-Solve
  ↓
Reflection
  ↓
Fake LLM 与自动化测试
  ↓
三种范式对比与选型
```

不建议一开始同时编写三种 Agent。如果底层 LLM 客户端、JSON 解析或工具参数校验还不稳定，Agent 循环中的错误会变得很难定位。

## 三、阶段一：搭建 Node.js + TypeScript 工程

### 第 1 步：检查开发环境

执行：

```bash
node --version
npm --version
```

建议 Node.js 20 或更高版本。原因是项目会使用 ESM、原生 `fetch`、`AbortSignal.timeout` 和新版 OpenAI SDK。

需要注意：

- Node.js 版本过低时，可能出现 `fetch is not defined`。
- 不要把 Node.js 运行时错误误判为 Agent 逻辑错误。
- 教学时先让所有学习者统一 Node.js 主版本。

### 第 2 步：进入项目并安装依赖

```bash
cd chapter4/agent-patterns-ts
npm install
```

主要依赖：

| 依赖 | 作用 |
|---|---|
| `openai` | 调用 OpenAI 或 OpenAI 兼容接口 |
| `dotenv` | 加载 `.env` 环境变量 |
| `zod` | 验证配置、工具参数和模型输出 |
| `tsx` | 开发期直接运行 TypeScript |
| `vitest` | 单元测试 |
| `typescript` | 静态类型检查 |

### 第 3 步：理解 ESM 导入规则

`package.json` 中使用：

```json
{
  "type": "module"
}
```

`tsconfig.json` 使用 `NodeNext`。因此 TypeScript 源码中的本地导入要写编译后的 `.js` 扩展名：

```ts
import type { LlmClient } from "./types.js";
```

而不是：

```ts
import type { LlmClient } from "./types";
```

这是初学者最容易遇到的问题之一。

### 第 4 步：建立阶段性验证习惯

每完成一个模块都执行：

```bash
npm run typecheck
npm test
```

教学时要强调：类型检查和测试不是最后一步，而是每个小步骤的收尾动作。

## 四、阶段二：配置模型服务

### 第 5 步：创建 `.env`

```bash
cp .env.example .env
```

典型配置：

```dotenv
LLM_API_KEY=你的密钥
LLM_MODEL_ID=模型ID
LLM_TIMEOUT_MS=60000

# 使用兼容 OpenAI 接口的第三方服务时填写
# LLM_BASE_URL=https://example.com/v1

# ReAct 搜索工具可选
# SERPAPI_API_KEY=你的SerpApi密钥
```

### 第 6 步：理解每个配置

`LLM_API_KEY`：身份认证凭证，不能写入源码，不能提交到 Git。

`LLM_MODEL_ID`：本次请求要调用的模型名称，必须与服务商实际提供的 ID 一致。

`LLM_BASE_URL`：SDK 发送请求的服务根地址。使用 OpenAI 官方服务时可以不填；使用 DeepSeek 等兼容 OpenAI 接口的服务时，填写对方文档提供的根地址。

`LLM_TIMEOUT_MS`：单次请求最长等待时间，项目中的单位是毫秒。

需要注意：

- `baseURL` 只改变请求发往哪里，不会自动把不兼容的 API 变成兼容 API。
- 第三方服务即使声称“OpenAI 兼容”，也可能不支持某些参数。
- `.env` 必须出现在 `.gitignore` 中。
- 单元测试不依赖 `.env`，只有真实 Demo 才使用它。

### 第 7 步：用 Zod 校验配置

核心文件：`src/core/config.ts`。

核心逻辑：

```ts
const envSchema = z.object({
  LLM_API_KEY: z.string().min(1),
  LLM_MODEL_ID: z.string().min(1),
  LLM_BASE_URL: z.string().url().optional(),
  LLM_TIMEOUT_MS: z.coerce.number().int().positive().default(60_000),
  SERPAPI_API_KEY: z.string().min(1).optional(),
});
```

Zod 在这里解决了一个关键问题：TypeScript 类型只在编译期存在，`.env`、HTTP 响应和 LLM 输出都是运行时数据，必须另外校验。

`z.coerce.number()` 很重要，因为 `process.env` 中的值默认都是字符串。

## 五、阶段三：封装基础 LLM 客户端

### 第 8 步：先定义项目内部协议

文件：`src/core/types.ts`。

```ts
export type MessageRole = "system" | "user" | "assistant";

export interface Message {
  role: MessageRole;
  content: string;
}

export interface LlmClient {
  generate(messages: Message[], temperature?: number): Promise<string>;
}

export interface AgentResult {
  answer: string;
  steps: number;
}
```

这一层抽象非常重要。ReAct、Plan-and-Solve 和 Reflection 只依赖 `LlmClient`，不依赖 OpenAI SDK。

它带来三个好处：

1. 可以替换 OpenAI 或第三方兼容服务。
2. 可以使用 Fake LLM 做单元测试。
3. Agent 的逻辑不需要知道 SDK 的流式响应结构。

### 第 9 步：实现 OpenAI 兼容客户端

文件：`src/core/openai-llm.ts`。

完整调用链：

```text
Agent 中的 Message[]
  → 转换成 SDK ChatCompletionMessageParam[]
  → chat.completions.create(..., stream: true)
  → for await 读取流式 chunk
  → chunk.choices[0]?.delta?.content
  → 一边输出，一边收集
  → join 成完整字符串
  → 返回给 Agent
```

核心请求：

```ts
const stream = await this.client.chat.completions.create({
  model: this.config.LLM_MODEL_ID,
  messages: sdkMessages,
  temperature,
  stream: true,
});
```

流式收集：

```ts
const collectedContent: string[] = [];

for await (const chunk of stream) {
  const content = chunk.choices[0]?.delta?.content ?? "";

  if (!content) {
    continue;
  }

  process.stdout.write(content);
  collectedContent.push(content);
}

const fullText = collectedContent.join("");
```

需要注意：

- 流式 chunk 只是增量片段，不是完整答案。
- `choices[0]` 可能不存在，所以使用可选链。
- 终端实时显示和程序最终返回是两件事，不能只 `write` 而不收集。
- 底层不应吞掉异常，记录后要继续 `throw`，让上层决定如何处理。

### 第 10 步：单独运行 LLM Demo

```bash
npm run demo:llm
```

这个阶段只验证五件事：

1. `.env` 是否成功加载。
2. API Key 是否有效。
3. Base URL 是否正确。
4. Model ID 是否可调用。
5. 流式输出是否能完整拼接。

不要在这一阶段同时调试 Agent，否则难以区分是网络配置还是 Agent 循环错误。

## 六、阶段四：实现通用 JSON 解析器

### 第 11 步：为什么 Agent 需要结构化输出

Agent 循环不能仅依赖自然语言去猜模型意图。例如 ReAct 要区分“调用工具”和“返回答案”，Reflection 要判断“是否需要继续优化”。

因此要经历：

```text
模型文本
  → 去掉 Markdown 代码围栏
  → JSON.parse
  → Zod Schema 校验
  → 类型安全的业务对象
```

### 第 12 步：实现 `parseJson`

文件：`src/core/json.ts`。

```ts
export function parseJson<T>(raw: string, schema: ZodType<T>): T {
  const cleaned = raw
    .trim()
    .replace(/^```(?:json)?\s*/i, "")
    .replace(/\s*```$/, "")
    .trim();

  let parsed: unknown;

  try {
    parsed = JSON.parse(cleaned);
  } catch (error: unknown) {
    const message = error instanceof Error ? error.message : String(error);
    throw new Error(`模型输出不是合法 JSON：${message}`);
  }

  return schema.parse(parsed);
}
```

需要注意：

- `JSON.parse` 只负责语法正确，不保证字段正确。
- Zod 才负责判断字段类型、枚举值、数组长度等业务约束。
- 清理 Markdown 围栏只是容错，提示词仍应要求模型只输出 JSON。

## 七、阶段五：实现工具系统

### 第 13 步：定义工具协议

文件：`src/tools/tool.ts`。

```ts
export interface Tool<TInput = unknown> {
  name: string;
  description: string;
  inputSchema: ZodType<TInput>;
  execute(input: TInput): Promise<string>;
}
```

每个工具都必须回答四个问题：

1. 我叫什么？
2. 我能做什么？
3. 我需要什么格式的参数？
4. 我被调用时如何执行？

### 第 14 步：实现 `ToolRegistry`

注册表负责：

- `register` 注册工具并阻止同名覆盖。
- `describe` 把工具列表转成模型可读的提示文本。
- `execute` 查找工具、校验参数、执行并将异常转成 Observation。

执行顺序：

```text
工具名 + unknown 参数
  → Map 查找
  → inputSchema.safeParse
  → tool.execute(parsed.data)
  → 字符串 Observation
```

这里使用 `safeParse` 而不是直接 `parse`，是因为工具参数错误是 Agent 循环中的可预期情况。错误信息应该作为 Observation 返回给模型，让它下一轮修正。

### 第 15 步：实现计算器工具

文件：`src/tools/calculator.ts`。

输入 Schema：

```ts
const calculatorInputSchema = z.object({
  left: z.number(),
  operator: z.enum(["+", "-", "*", "/"]),
  right: z.number(),
});
```

教学示例：

```json
{
  "left": 30,
  "operator": "-",
  "right": 5
}
```

执行结果：

```text
25
```

需要注意：

- 除数为 0 要显式报错。
- 不要使用 `eval` 执行模型生成的字符串表达式。
- 工具输出统一转为字符串，便于放入后续提示词。

### 第 16 步：实现搜索工具

文件：`src/tools/search.ts`。

搜索工具的教学目标不只是“能搜索”，而是学习如何把外部 HTTP 服务封装成 Agent 工具。

流程：

```text
{"query":"搜索词"}
  → Zod 校验
  → 构建 URL 和查询参数
  → fetch
  → 检查 HTTP 状态
  → 解析 JSON
  → 优先取 answer box / knowledge graph
  → 否则整理前 3 条结果
  → 返回简短 Observation
```

需要注意：

- 搜索结果不要无限量放入上下文，否则会增加 token 消耗。
- 搜索服务密钥不应出现在工具源码中。
- HTTP 错误应该转成可理解的 Observation。
- 模型根据搜索摘要生成答案，并不代表信息必然真实，生产系统还要增加来源、时间和交叉验证。

## 八、阶段六：实现 ReAct

### 第 17 步：理解 ReAct 数据流

ReAct 的核心是：

```text
Question
  → Thought
  → Action
  → Observation
  → Thought
  → ...
  → Final Answer
```

项目中不直接解析自然语言标签，而是要求模型输出两种 JSON 决策之一。

调用工具：

```json
{
  "type": "tool",
  "thought": "需要计算 2 + 3",
  "tool": "calculator",
  "input": {
    "left": 2,
    "operator": "+",
    "right": 3
  }
}
```

完成任务：

```json
{
  "type": "finish",
  "thought": "已经得到所需信息",
  "answer": "2 + 3 = 5"
}
```

### 第 18 步：用可辨识联合定义决策

文件：`src/agents/react/react-agent.ts`。

```ts
export const reactDecisionSchema = z.discriminatedUnion("type", [
  z.object({
    type: z.literal("tool"),
    thought: z.string().min(1),
    tool: z.string().min(1),
    input: z.unknown(),
  }),
  z.object({
    type: z.literal("finish"),
    thought: z.string().min(1),
    answer: z.string().min(1),
  }),
]);
```

`type` 是判别字段。校验成功后，TypeScript 可以根据 `decision.type` 自动知道当前对象有 `tool/input` 还是 `answer`。

### 第 19 步：实现 ReAct 循环

每轮执行：

1. 把用户问题和历史 Observation 发给 LLM。
2. 用 `parseJson` 解析决策。
3. 如果是 `finish`，返回 `AgentResult`。
4. 如果是 `tool`，通过注册表执行工具。
5. 把 Thought、Action 和 Observation 追加到历史。
6. 进入下一轮。

必须设置 `maxSteps`：

```ts
for (let currentStep = 1; currentStep <= maxSteps; currentStep += 1) {
  // 调用模型、解析决策、执行工具或结束
}
```

如果不设最大步数，模型可能重复调用同一工具，导致无限循环和不可控费用。

### 第 20 步：运行 ReAct 计算示例

```bash
npm run demo:react -- "计算 15 * 2，再减去 5"
```

学习者应观察：

1. 模型是否先调用 `calculator`。
2. 第一次 Observation 是否为 `30`。
3. 第二次计算是否使用上一轮结果 `30`。
4. 最后是否输出 `finish`。

### 第 21 步：运行 ReAct 搜索示例

```bash
npm run demo:react -- "查询当前最新的主流GPU型号，并总结主要特点"
```

这个命令的参数传递链是：

```text
终端字符串
  → npm 的 -- 将后续参数转发给 tsx
  → Node.js process.argv
  → process.argv.slice(2)
  → join(" ")
  → agent.run(question)
  → ReActAgent.run 中的 question
  → 用户提示词
```

`--` 很重要，它表示后面的内容不再由 npm 解析，而是传递给真正运行的脚本。

当问题包含空格时应加引号，保证它是一个完整参数。

### 第 22 步：理解 ReAct 测试案例

`tests/react-agent.test.ts` 中的核心用例预置两个模型回复：

```text
第 1 次回复：调用 calculator
第 2 次回复：根据 Observation 返回 finish
```

测试不仅断言最终答案，还检查第二次 LLM 调用的用户消息中包含：

```text
Observation: 5
```

这个断言验证的是 ReAct 的核心数据流，而不只是某个结果字符串。

## 九、阶段七：实现 Plan-and-Solve

### 第 23 步：理解 Plan-and-Solve 数据流

```text
Question
  → Planner
  → [Step 1, Step 2, Step 3]
  → Executor 执行 Step 1
  → 保存 Result 1
  → Executor 执行 Step 2，并携带 Result 1
  → ...
  → 最后步骤结果
```

ReAct 是边执行边决定下一步，Plan-and-Solve 是执行前先把计划生成完整。

### 第 24 步：定义计划和历史类型

文件：`src/agents/plan-and-solve/types.ts`。

```ts
export const planSchema = z.object({
  steps: z.array(z.string().trim().min(1)).min(1).max(12),
});

export interface StepRecord {
  stepNumber: number;
  step: string;
  result: string;
}
```

`min(1)` 防止空计划，`max(12)` 防止模型生成过长计划导致大量串行调用。

### 第 25 步：实现 Planner

文件：`src/agents/plan-and-solve/planner.ts`。

Planner 的唯一职责是拆解任务，不解答任务。

输入：

```text
计算水果店三天的苹果总销量
```

期望输出：

```json
{
  "steps": [
    "计算周二卖出的苹果数量",
    "计算周三卖出的苹果数量",
    "计算三天总销量"
  ]
}
```

Planner 的处理顺序：

1. `trim` 并拒绝空问题。
2. 组装 Planner 系统消息和用户消息。
3. 以低温度调用 LLM。
4. 用 `parseJson(rawResponse, planSchema)` 解析。
5. 返回 `string[]`。
6. 解析失败时包装为带上下文的 Planner 错误。

### 第 26 步：实现 Executor

文件：`src/agents/plan-and-solve/executor.ts`。

Executor 的唯一职责是按顺序执行已有计划。

每次调用 LLM 都传入：

- 原始问题。
- 完整计划。
- 已经完成的步骤与结果。
- 当前步骤。

水果店示例的执行轨迹：

```text
步骤 1：计算周二销量
结果：30

步骤 2：计算周三销量
已知历史：步骤 1 结果为 30
结果：25

步骤 3：计算三天总销量
已知历史：15、30、25
结果：70
```

需要注意：后续步骤必须看到前面的结果。如果只传当前步骤，模型只会得到多个孤立的子任务。

### 第 27 步：组合 Planner 和 Executor

文件：`src/agents/plan-and-solve/plan-and-solve-agent.ts`。

```ts
const plan = await this.planner.plan(normalizedQuestion);
const execution = await this.executor.execute(normalizedQuestion, plan);

return {
  answer: execution.finalAnswer,
  steps: plan.length,
};
```

这个类只负责编排流程，不重复 Planner 和 Executor 的细节。

### 第 28 步：运行 Plan-and-Solve Demo

```bash
npm run demo:plan
```

或：

```bash
npm run demo:plan -- "为一次Node.js项目上线制定检查计划"
```

学习者要分别观察 Planner 输出和每个 Executor 结果，不要只看最后答案。

### 第 29 步：逐条理解 `planner.test.ts`

`tests/planner.test.ts` 使用 AAA 模式：

```text
Arrange：准备 Fake LLM、Planner 和输入
Act：调用 planner.plan(...)
Assert：检查返回计划、错误或调用次数
```

用例一：合法 JSON。

- Fake LLM 返回包含 3 个步骤的 JSON。
- Planner 应该解析成字符串数组。
- LLM 只能被调用 1 次。

用例二：空计划。

- JSON 语法正确，但 `steps: []` 违反 Zod 的 `.min(1)`。
- 这个用例说明“合法 JSON”不等于“合法业务数据”。

用例三：非法 JSON。

- Fake LLM 返回普通文本。
- `JSON.parse` 失败。
- Planner 应抛出带有“无法解析计划”语义的错误。

用例四：空问题。

- Planner 在调用 LLM 前失败。
- `llm.calls` 长度必须为 0。
- 这个断言证明输入校验确实发生在外部调用之前。

自己增加 Planner 测试时，可以继续覆盖：

- 1 个步骤的最小合法计划。
- 12 个步骤的上界。
- 13 个步骤的越界计划。
- 包含空字符串步骤的计划。
- 被 Markdown JSON 围栏包裹的计划。

## 十、阶段八：实现 Reflection

### 第 30 步：理解 Reflection 数据流

```text
原始任务
  → 生成初稿 O0
  → 评审 O0，得到 F0
  → 如果不需改进，返回 O0
  → 如果需要改进，根据 F0 生成 O1
  → 评审 O1，得到 F1
  → ...
  → 评审通过或达到最大反思次数
```

Reflection 不是无限“想得更多”，而是必须有评价标准、运行记录、停止信号和最大迭代次数的受控改进循环。

### 第 31 步：定义反思决策

文件：`src/agents/reflection/types.ts`。

```ts
export const reflectionDecisionSchema = z
  .object({
    needsImprovement: z.boolean(),
    feedback: z.string().trim().min(1),
  })
  .strict();
```

评审模型必须返回：

```json
{
  "needsImprovement": true,
  "feedback": "当前算法采用逐个试除，建议改用埃拉托斯特尼筛法。"
}
```

不要仅用 `feedback.includes("无需改进")` 作为终止条件，因为自然语言可能出现否定、改写或模糊表达。布尔字段更适合程序判断。

### 第 32 步：实现短期记忆

文件：`src/agents/reflection/memory.ts`。

记忆中只保存两类记录：

```ts
export type MemoryKind = "execution" | "reflection";
```

`add` 保存一条记录，`latestExecution` 从后向前找到最新版本，`trajectory` 将整个过程序列化为可放入提示词的文本。

需要注意：每次 `run()` 都应创建新的记忆对象，否则同一 Agent 实例连续执行两个任务时，可能发生记忆污染。

### 第 33 步：拆分三类提示词

文件：`src/agents/reflection/prompts.ts`。

| 提示词 | 角色 | 输出 |
|---|---|---|
| Initial Execution | Python 程序员 | 第一版代码 |
| Reflection | 严格代码评审员 | JSON 决策和反馈 |
| Refinement | Python 程序员 | 根据反馈修改后的完整代码 |

三个阶段不能混用同一段含糊提示词。评审阶段的职责是找问题和提建议，不是直接重写代码。

### 第 34 步：实现 ReflectionAgent

文件：`src/agents/reflection/reflection-agent.ts`。

主流程伪代码：

```ts
const memory = new ShortTermMemory();
const initialDraft = await generateInitialDraft(task);
memory.add({ kind: "execution", content: initialDraft });

for (let iteration = 0; iteration < maxIterations; iteration += 1) {
  const currentDraft = memory.latestExecution();
  const rawReflection = await review(task, currentDraft);
  const decision = parseJson(rawReflection, reflectionDecisionSchema);

  memory.add({
    kind: "reflection",
    content: JSON.stringify(decision, null, 2),
  });

  if (!decision.needsImprovement) {
    break;
  }

  const refinedDraft = await refine(
    task,
    currentDraft,
    decision.feedback,
    memory.trajectory(),
  );

  memory.add({ kind: "execution", content: refinedDraft });
}

return memory.latestExecution();
```

### 第 35 步：运行素数代码优化示例

```bash
npm run demo:reflection -- "编写一个Python函数，找出1到n之间所有素数，要求考虑算法效率和边界情况"
```

典型过程：

```text
第 1 次调用：生成试除法初稿
第 2 次调用：评审指出时间复杂度问题
第 3 次调用：修改为埃拉托斯特尼筛法
第 4 次调用：评审修改后版本
如果 needsImprovement=false：停止
```

反思轮数为 `R` 时：

```text
总调用次数 = 1 次初稿 + R 次反思 + U 次优化
```

其中 `0 <= U <= R`。当 `maxIterations = 2` 时，最多调用 5 次。

### 第 36 步：理解 Reflection 测试

`tests/reflection-agent.test.ts` 应覆盖：

1. 初稿第一次评审就通过，总调用数为 2。
2. 第一轮要求改进，优化后第二轮通过，总调用数为 4。
3. 每轮都要改进，达到最大迭代数后返回最后一版。
4. 评审返回非法 JSON 时抛出可读错误。
5. 空任务在调用 LLM 之前失败。

还要检查优化阶段的提示词中确实包含：

- 原始任务。
- 上一版代码。
- 当前反馈。
- 历史执行与反思轨迹。

## 十一、阶段九：用 Fake LLM 学习测试

### 第 37 步：实现可预测的模型替身

文件：`tests/helpers/fake-llm.ts`。

```ts
export class FakeLlmClient implements LlmClient {
  public readonly calls: Message[][] = [];

  public constructor(private readonly replies: string[]) {}

  public async generate(messages: Message[]): Promise<string> {
    this.calls.push(messages.map((message) => ({ ...message })));

    const reply = this.replies.shift();

    if (reply === undefined) {
      throw new Error("FakeLlmClient 响应已耗尽");
    }

    return reply;
  }
}
```

Fake LLM 有两个功能：

1. 按顺序返回预先准备的文本。
2. 保存每次调用收到的消息，便于检查上下文是否正确传递。

如果一个测试预期有 4 次 LLM 调用，就必须提供 4 个回复。回复数不足时抛错，可以帮助发现 Agent 出现了额外调用。

### 第 38 步：使用 AAA 结构自己写测试

每个测试按以下顺序编写：

```ts
it("用例描述", async () => {
  // Arrange：准备假回复、依赖和输入。

  // Act：调用被测试方法。

  // Assert：检查输出、异常和交互。
});
```

一个 Agent 用例通常需要检查三层：

1. 返回值是否正确。
2. LLM 或工具的调用次数是否正确。
3. 后续调用是否收到了前面的 Observation、步骤结果或反思反馈。

### 第 39 步：为每个模块建立测试矩阵

| 模块 | 正常路径 | 边界 | 异常 | 交互 |
|---|---|---|---|---|
| ToolRegistry | 注册并执行 | 空注册表 | 同名、错参数 | Schema 是否生效 |
| ReAct | tool 后 finish | 最大步数 | 非法 JSON、未知工具 | Observation 是否回传 |
| Planner | 合法计划 | 1/12 步 | 空计划、非法 JSON | LLM 调用次数 |
| Executor | 按序执行 | 单步计划 | 空计划、空结果 | 前步结果是否传递 |
| Reflection | 反思后优化 | 首轮通过、达上限 | 非法反思 JSON | 反馈和轨迹是否传递 |

## 十二、三种 Agent 的教学对比

| 维度 | ReAct | Plan-and-Solve | Reflection |
|---|---|---|---|
| 核心流程 | 思考—行动—观察 | 规划—顺序执行 | 初稿—反思—优化 |
| 下一步何时决定 | 每轮动态决定 | 开始时一次规划 | 根据评审反馈决定 |
| 外部工具 | 通常需要 | 本例中不需要 | 本例中不需要 |
| 主要记忆 | Action/Observation 轨迹 | 计划步骤结果 | 执行版本与反思反馈 |
| 停止条件 | finish 或 maxSteps | 计划执行完毕 | 评审通过或 maxIterations |
| 主要优势 | 能根据工具结果调整 | 多步任务结构清晰 | 显著提高初稿质量 |
| 主要局限 | 可能循环或乱调工具 | 初始计划错后续都受影响 | 成本和延迟高 |
| 典型场景 | 搜索、查询、计算、工具操作 | 报告、调研、静态任务分解 | 代码、文章、重要方案改进 |

### 选型方法

需要根据外部反馈动态决策：优先 ReAct。

任务可以提前拆解，并且步骤相对稳定：优先 Plan-and-Solve。

初稿容易产生细节或质量问题，且值得用额外调用换质量：优先 Reflection。

复杂工程中可以组合：

```text
Plan-and-Solve 生成计划
  → 每个步骤使用 ReAct 获取工具反馈
  → 对最终结果使用 Reflection 评审与优化
```

但组合不是越多越好，必须同时设定总调用数、总 token、超时和错误处理策略。

## 十三、重要注意事项

### 1. TypeScript 类型不能代替 Zod

TypeScript 不能在运行时验证 LLM 输出和 HTTP 响应。所有外部数据进入业务逻辑前都应通过 Schema。

### 2. 结构化输出仍然会失败

提示词要求输出 JSON 不代表每次都会正确。应根据场景选择：

- ReAct：将格式错误加入 Observation，给模型一次自我修正机会。
- Planner：规划格式错误时立即失败，由上层决定是否重试。
- Reflection：评审决策无法解析时停止，避免用不可信反馈继续修改。

### 3. 所有循环都必须有上限

ReAct 用 `maxSteps`，Reflection 用 `maxIterations`，Plan-and-Solve 用计划步骤上限。

上限不只是防止死循环，也是成本、延迟和风险边界。

### 4. 调试时先看数据流

不要只看最后答案。要检查：

- ReAct 后一轮是否看到 Observation。
- Executor 后一步是否看到前一步结果。
- Refinement 是否看到上一版、反馈和轨迹。

最终答案偶然正确，不能证明 Agent 数据流正确。

### 5. 单元测试不要调用真实 LLM

真实 LLM 存在不确定性、网络延迟、调用费用和限流。单元测试要测的是程序的状态转移，不是模型的即时能力。

真实 API 测试应单独放在手动 Demo 或集成测试中。

### 6. 温度要根据阶段设置

- JSON 决策、规划、评审：建议从 `0` 开始。
- 文章或代码初稿：可以使用较低的非零温度，如 `0.2`。
- 不要认为温度为 0 就能保证完全确定。

### 7. 提示词要写清输入、职责、输出和停止条件

一个稳定的 Agent 提示词至少应说清：

1. 当前角色是什么。
2. 当前阶段只负责什么。
3. 可用数据或工具是什么。
4. 输出必须遵循什么格式。
5. 什么时候应该停止。

### 8. 上下文不是越多越好

历史轨迹可以提供信息，但也会增加 token 成本和噪声。生产化时要考虑：

- 只保留最近几轮。
- 对旧轨迹做摘要。
- 对工具返回做截断和结构化提取。
- 不向反思模型反复传入与当前评审无关的数据。

### 9. 工具执行需要安全边界

计算器和搜索属于低风险工具。如果未来添加文件删除、数据库写入、邮件发送或付款等工具，不能仅依赖模型自主决定，还要增加权限、人工确认、审计记录和幂等保护。

### 10. 成本与延迟必须被测量

不要只比较答案质量，还要记录：

- LLM 调用次数。
- 输入和输出 token。
- 工具调用次数。
- 总耗时。
- 重试次数。
- 最终任务成功率。

Reflection 尤其需要注意这一点，因为它用额外的串行调用换取质量。

## 十四、常见问题与排查顺序

### 问题 1：真实 Demo 无法调用模型

按以下顺序排查：

1. `.env` 是否在项目根目录。
2. `LLM_API_KEY` 是否为空。
3. `LLM_MODEL_ID` 是否为服务商真实模型 ID。
4. 第三方服务的 `LLM_BASE_URL` 是否正确。
5. 服务是否支持 `chat.completions`。
6. 是否存在超时、限流、余额或网络问题。

### 问题 2：模型总是在 JSON 外面添加解释

1. 在系统提示词中明确要求只输出 JSON。
2. 给出唯一的 JSON 字段结构。
3. 使用低温度。
4. 保留 `parseJson` 的 Markdown 围栏容错。
5. 如果服务商支持原生结构化输出，生产项目可进一步使用其 Schema 能力。

### 问题 3：ReAct 重复调用同一工具

1. 检查 Observation 是否放入下一轮提示词。
2. 检查工具输出是否包含有用信息。
3. 提示模型不要重复已成功的操作。
4. 保留 `maxSteps`。
5. 必要时记录已执行的“工具名 + 参数”并阻止无意义重复。

### 问题 4：Plan-and-Solve 后续步骤丢失上文

1. 检查 `history.push(record)` 是否在每步执行后发生。
2. 检查 `createExecutorUserPrompt` 是否包含 `formatHistory(history)`。
3. 在测试中检查第二次 LLM 调用是否含有第一步结果。

### 问题 5：Reflection 永远说需要改进

1. 保留 `maxIterations`。
2. 将评价维度和“足够好”的标准写清楚。
3. 要求反馈具体、可操作，避免泛化建议。
4. 检查优化提示词是否真正包含上一轮反馈。
5. 如果每轮只做无实质修改的改写，可加入分数改善阈值或内容变化阈值。

### 问题 6：测试报 `FakeLlmClient 响应已耗尽`

这说明 Agent 实际调用次数超过了测试中准备的回复数。

先写出预期时序：

```text
调用 1 应返回什么
调用 2 应返回什么
调用 3 应返回什么
```

然后一一对应填写 `replies`，不要随意多加回复掩盖逻辑问题。

# 学习总结

## 1. Agent 的本质是受控状态循环

普通 LLM 应用通常是一次输入和一次输出。Agent 在这个基础上加入了状态、外部行动、中间结果和停止条件。

真正值得学习的不是 Agent 类的名称，而是：

- 什么数据是当前状态。
- 模型可以做出哪些决策。
- 决策如何被验证。
- 外部执行结果如何回传。
- 循环在什么条件下结束。

## 2. ReAct 的学习核心是外部反馈

ReAct 让模型不必把所有事实都存在参数中，而是通过工具获取计算、搜索或其他系统的反馈。关键不是“能调用工具”，而是“能把 Observation 放回下一轮决策”。

## 3. Plan-and-Solve 的学习核心是职责分离

Planner 只制定计划，Executor 只执行当前步骤，组合 Agent 只负责编排。这种拆分让每一层都可以独立测试，也让错误定位更清晰。

## 4. Reflection 的学习核心是评价驱动的迭代

Reflection 的价值是将“一次生成”变成“按明确标准反复改进”。它的效果高度依赖评审标准和反馈质量，并且必须用迭代上限控制成本。

## 5. Zod 是 LLM 与程序之间的边界

模型输出本质上是不可信文本。只有经过 JSON 语法解析和 Zod 业务校验后，它才能变成程序可以安全使用的决策。

同样的原则也适用于环境变量、工具参数、HTTP 响应和持久化数据。

## 6. 测试要验证过程，不只是结果

对 Agent 而言，一个正确的最终答案可能是偶然得到的。因此测试还应验证调用次数、调用顺序和上下文传递。

Fake LLM 使模型回复变成可预测输入，从而让我们把测试重点放在 Agent 程序本身。

## 7. 工程化的关键是边界和可观测性

一个可用的 Agent 除了提示词之外，还必须具有：

- 输入校验。
- 结构化决策。
- 工具参数校验。
- 超时和循环上限。
- 错误传递与分类。
- 轨迹记录。
- 可预测测试。
- 成本、耗时和调用次数统计。

## 8. 最终结论

本章通过亲手实现三种范式，完成了从“调用一次模型”到“构建可控智能体循环”的转变。

可以用三句话记住三种范式：

```text
ReAct：我下一步需要做什么，工具刚才告诉了我什么？

Plan-and-Solve：这个问题应该先分成哪些步骤，然后如何按顺序完成？

Reflection：当前答案还有什么明确问题，如何根据反馈产生更好版本？
```

当学习者能够清楚画出每种范式的状态、输入、输出、循环边界和测试方法时，才算真正掌握了本章内容。
