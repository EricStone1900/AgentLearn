# 第四章 智能体经典范式实现流程

本文是《第四章 智能体经典范式构建》的 Node.js + TypeScript 配套实践手册。目标不是直接依赖 LangChain 等高级框架，而是亲手实现模型调用、工具管理、输出解析、状态记录和 Agent 循环，从而理解智能体的内部工作机制。

配套工程位于：

```text
chapter4/agent-patterns-ts
```

建议严格按照本文顺序操作。每完成一个阶段，先运行类型检查和测试，再进入下一阶段。不要同时编写三个 Agent，否则出现问题时很难判断错误来自模型调用、输出解析、工具执行还是循环控制。

---

## 一、最终要实现什么

本项目最终实现三种经典 Agent 范式：

1. **ReAct**：通过“思考 → 行动 → 观察”循环，一边使用工具，一边调整后续决策。
2. **Plan-and-Solve**：先把复杂问题拆成完整计划，再根据计划逐步执行。
3. **Reflection**：先生成初稿，再通过“执行 → 反思 → 优化”循环提高结果质量。

## 二、阶段一：准备 Node.js 与 TypeScript 工程

### 第 1 步：确认开发环境

建议使用 Node.js 20 或更高版本。

```bash
node --version
npm --version
```

为什么要先检查版本：

- Node.js 20 以上可以直接使用原生 `fetch`，实现搜索工具时不必额外安装 HTTP 库。
- 新版 TypeScript、OpenAI SDK 和测试框架通常要求较新的 Node.js 版本。
- 提前确认环境，可以避免把运行时兼容问题误判为 Agent 逻辑错误。

### 第 2 步：进入工程并安装依赖

```bash
cd chapter4/agent-patterns-ts
npm install
```

本项目主要使用以下依赖：

- `openai`：调用 OpenAI 或兼容接口。
- `dotenv`：从 `.env` 加载配置。
- `zod`：验证环境变量、工具参数和模型结构化输出。
- `typescript`：TypeScript 编译器。
- `tsx`：开发阶段直接运行 TypeScript。
- `vitest`：编写无需真实 API 的单元测试。

### 第 3 步：理解 TypeScript 配置

打开 `tsconfig.json`，重点关注：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true
  }
}
```

为什么这样设置：

- `NodeNext` 让 TypeScript 按照 Node.js 的 ESM 规则处理模块。
- `strict` 可以尽早发现空值、参数类型和返回值错误。
- `noUncheckedIndexedAccess` 会提醒我们：数组或 Map 中不一定存在目标数据。这对计划步骤、模型响应队列等代码很重要。
- 本地模块导入写成 `./types.js`，是因为编译后的 JavaScript 文件扩展名是 `.js`。

### 第 4 步：执行第一次验证

```bash
npm run dev
npm run typecheck
npm test
```

此时只需要看到工程能够启动、类型检查通过、骨架测试通过。这个阶段不应调用真实模型。

## 四、阶段三：封装统一的 LLM 客户端

### 第 7 步：定义模型抽象接口

文件：`src/core/types.ts`

核心接口如下：

```ts
export type MessageRole = "system" | "user" | "assistant";

export interface Message {
  role: MessageRole;
  content: string;
}

export interface LlmClient {
  generate(messages: Message[]): Promise<string>;
}
```

为什么不让 Agent 直接使用 OpenAI SDK：

- ReAct、Plan-and-Solve 和 Reflection 只需要“输入消息、返回文本”这一能力。
- 更换模型服务时只修改适配层，不修改三个 Agent。
- 测试时可以传入假模型，不产生网络请求和 API 费用。

这是一种典型的依赖倒置：Agent 依赖接口，而不是依赖具体 SDK。

### 第 8 步：实现模型调用

文件：`src/core/openai-llm.ts`

找到：

```bash
rg 'TODO\(step-02\)' src/core
```

把 `generate` 实现为：

```ts
public async generate(messages: Message[]): Promise<string> {
  const response = await this.client.responses.create({
    model: this.config.LLM_MODEL_ID,
    input: messages.map(({ role, content }) => ({ role, content })),
  });

  const text = response.output_text.trim();
  if (!text) {
    throw new Error("模型返回了空文本");
  }
  return text;
}
```

为什么在这里检查空文本：

- 空文本对所有 Agent 都没有意义。
- 在适配层统一处理，三个 Agent 不必重复判断。
- 网络异常、超时和 SDK 异常也应该从这一层向上抛出，由入口统一记录。

如果所使用的兼容服务不支持 Responses API，只修改 `OpenAiLlmClient` 内部实现，不要修改 `LlmClient` 接口和 Agent。

### 第 9 步：实现结构化 JSON 解析器

文件：`src/core/json.ts`

模型有时会在 JSON 外包裹 Markdown 代码围栏，因此先清理围栏，再解析和验证：

```ts
import type { ZodType } from "zod";

export function parseJson<T>(raw: string, schema: ZodType<T>): T {
  const cleaned = raw
    .trim()
    .replace(/^```(?:json)?\s*/i, "")
    .replace(/\s*```$/, "")
    .trim();

  let value: unknown;
  try {
    value = JSON.parse(cleaned);
  } catch (error) {
    throw new Error(
      `模型输出不是合法 JSON：${error instanceof Error ? error.message : String(error)}`,
    );
  }

  return schema.parse(value);
}
```

为什么不能写成：

```ts
return JSON.parse(raw) as T;
```

因为 `as T` 只影响编译器，不会检查运行时数据。模型可能遗漏字段、返回错误类型或产生不存在的动作。JSON 解决“文本格式”问题，Zod 解决“数据结构”问题。

## 五、阶段四：实现工具系统

工具是智能体与外部环境交互的“手和脚”。每个工具至少需要名称、描述、参数 Schema 和执行函数。

### 第 11 步：定义工具协议

文件：`src/tools/tool.ts`

```ts
export interface Tool<TInput = unknown> {
  name: string;
  description: string;
  inputSchema: ZodType<TInput>;
  execute(input: TInput): Promise<string>;
}
```

各字段的作用：

- `name`：模型在 Action 中使用的唯一标识。
- `description`：告诉模型何时应该使用该工具。
- `inputSchema`：在工具边界上校验不可信参数。
- `execute`：真正执行查询或操作。

工具描述非常重要。如果描述含糊，即使执行代码完全正确，模型也可能选择错误工具。

### 第 12 步：实现工具注册表

把 `ToolRegistry` 完成为：

```ts
export class ToolRegistry {
  private readonly tools = new Map<string, Tool<any>>();

  public register<TInput>(tool: Tool<TInput>): void {
    if (this.tools.has(tool.name)) {
      throw new Error(`工具已存在：${tool.name}`);
    }
    this.tools.set(tool.name, tool);
  }

  public describe(): string {
    if (this.tools.size === 0) return "当前没有可用工具";
    return [...this.tools.values()]
      .map((tool) => `- ${tool.name}: ${tool.description}`)
      .join("\n");
  }

  public async execute(name: string, input: unknown): Promise<string> {
    const tool = this.tools.get(name);
    if (!tool) return `错误：不存在名为 ${name} 的工具`;

    const parsed = tool.inputSchema.safeParse(input);
    if (!parsed.success) {
      return `错误：工具 ${name} 的参数不合法：${parsed.error.message}`;
    }

    try {
      return await tool.execute(parsed.data);
    } catch (error) {
      return `错误：工具 ${name} 执行失败：${
        error instanceof Error ? error.message : String(error)
      }`;
    }
  }
}
```

为什么工具错误要转成字符串 Observation，而不是直接结束进程：

- ReAct 可以读取错误原因，在下一轮修正工具名或参数。
- 工具异常不一定意味着整个任务无法完成。
- 所有工具使用统一错误格式，便于日志记录和测试。

对于支付、删除数据、发送邮件等高风险工具，不能简单自动重试，还需要权限检查、幂等设计和人工确认。

### 第 13 步：实现计算器工具

文件：`src/tools/calculator.ts`

```ts
async execute(input) {
  let result: number;

  switch (input.operator) {
    case "+":
      result = input.left + input.right;
      break;
    case "-":
      result = input.left - input.right;
      break;
    case "*":
      result = input.left * input.right;
      break;
    case "/":
      if (input.right === 0) throw new Error("除数不能为 0");
      result = input.left / input.right;
      break;
  }

  return String(result);
}
```

不要使用：

```ts
eval(modelGeneratedExpression)
```

模型输出属于不可信输入，`eval` 可能执行任意 JavaScript。将输入限制为两个数字和一个枚举运算符，安全边界更清楚。

### 第 14 步：实现搜索工具

新建 `src/tools/search.ts`：

```ts
import { z } from "zod";
import type { Tool } from "./tool.js";

const searchInputSchema = z.object({
  query: z.string().min(1),
});

type SearchInput = z.infer<typeof searchInputSchema>;

export const searchTool: Tool<SearchInput> = {
  name: "search",
  description: "搜索实时信息、新闻和模型知识库中可能不存在的事实",
  inputSchema: searchInputSchema,

  async execute({ query }) {
    const apiKey = process.env.SERPAPI_API_KEY;
    if (!apiKey) throw new Error("缺少 SERPAPI_API_KEY");

    const url = new URL("https://serpapi.com/search.json");
    url.searchParams.set("engine", "google");
    url.searchParams.set("q", query);
    url.searchParams.set("api_key", apiKey);
    url.searchParams.set("hl", "zh-cn");
    url.searchParams.set("gl", "cn");

    const response = await fetch(url);
    if (!response.ok) {
      throw new Error(`搜索服务返回 HTTP ${response.status}`);
    }

    const data = (await response.json()) as {
      answer_box?: { answer?: string };
      knowledge_graph?: { description?: string };
      organic_results?: Array<{ title?: string; snippet?: string }>;
    };

    if (data.answer_box?.answer) return data.answer_box.answer;
    if (data.knowledge_graph?.description) {
      return data.knowledge_graph.description;
    }

    const results = data.organic_results?.slice(0, 3) ?? [];
    if (results.length === 0) return "没有找到相关结果";

    return results
      .map((item, index) =>
        `${index + 1}. ${item.title ?? "无标题"}\n${item.snippet ?? "无摘要"}`,
      )
      .join("\n\n");
  },
};
```

搜索结果优先选择直接答案或知识图谱，否则返回前三条摘要。这样可以减少无关文本进入模型上下文。

## 六、阶段五：实现 ReAct 智能体

ReAct 的核心不是一次生成答案，而是循环执行：

```text
Thought → Action → Observation → Thought → ... → Finish
```

### 第 16 步：定义模型决策协议

文件：`src/agents/react/react-agent.ts`

工程已经定义两种合法输出：

```ts
export const reactDecisionSchema = z.discriminatedUnion("type", [
  z.object({
    type: z.literal("tool"),
    thought: z.string(),
    tool: z.string(),
    input: z.unknown(),
  }),
  z.object({
    type: z.literal("finish"),
    thought: z.string(),
    answer: z.string(),
  }),
]);
```

模型调用工具时返回：

```json
{
  "type": "tool",
  "thought": "需要精确计算",
  "tool": "calculator",
  "input": { "left": 123, "operator": "+", "right": 456 }
}
```

任务完成时返回：

```json
{
  "type": "finish",
  "thought": "信息已经足够",
  "answer": "最终答案"
}
```

原章节使用正则表达式解析 `Thought` 和 `Action`。本项目使用 JSON + Zod，原因是自然语言格式容易受换行、中文标点和模型习惯影响。二者的核心思想相同，都是把模型输出转换成程序可执行的动作。

### 第 17 步：设计 ReAct 提示词

提示词必须包含：

1. Agent 的角色。
2. 当前可用工具及其描述。
3. 两种合法 JSON 格式。
4. 只能选择已有工具。
5. 工具失败后要根据 Observation 修正。
6. 信息充足时必须输出 `finish`。

示例：

```ts
const systemPrompt = `
你是一个可以调用外部工具解决问题的智能助手。

可用工具：
${this.tools.describe()}

每轮只能输出一个 JSON 对象，不能输出 Markdown，也不能添加额外说明。

调用工具：
{"type":"tool","thought":"简短说明","tool":"工具名","input":{}}

完成任务：
{"type":"finish","thought":"简短说明","answer":"最终答案"}

如果 Observation 包含错误，请修正工具名或参数后再尝试。
不要调用不存在的工具。
`;
```

### 第 18 步：实现 ReAct 主循环

在 `run` 中实现：

```ts
public async run(question: string): Promise<AgentResult> {
  const maxSteps = this.options.maxSteps ?? 6;
  const trajectory: string[] = [];

  for (let step = 1; step <= maxSteps; step += 1) {
    const raw = await this.llm.generate([
      { role: "system", content: systemPrompt },
      {
        role: "user",
        content: [
          `用户问题：${question}`,
          "已有轨迹：",
          trajectory.length > 0 ? trajectory.join("\n") : "暂无",
        ].join("\n"),
      },
    ]);

    let decision;
    try {
      decision = parseJson(raw, reactDecisionSchema);
    } catch (error) {
      trajectory.push(
        `Observation: 输出格式错误，请严格返回规定 JSON。${
          error instanceof Error ? error.message : String(error)
        }`,
      );
      continue;
    }

    if (decision.type === "finish") {
      return { answer: decision.answer, steps: step };
    }

    const observation = await this.tools.execute(
      decision.tool,
      decision.input,
    );

    trajectory.push(
      `Thought: ${decision.thought}\n` +
      `Action: ${decision.tool} ${JSON.stringify(decision.input)}\n` +
      `Observation: ${observation}`,
    );
  }

  throw new Error(
    `ReAct 达到最大步骤数仍未完成。\n${trajectory.join("\n")}`,
  );
}
```

将上面使用的 `systemPrompt` 放在循环外部，避免每轮重复构造不变内容。

为什么必须设置 `maxSteps`：

- 模型可能重复调用同一工具。
- 工具可能持续返回无效结果。
- 模型可能始终不生成 `finish`。
- 没有上限会不断消耗时间和 API 费用。

为什么 Observation 必须加入下一轮提示词：

如果模型看不到工具结果，它就无法根据环境反馈调整推理，整个循环会退化成重复生成。

### 第 19 步：运行 ReAct 示例

在入口中注册工具：

```ts
const tools = new ToolRegistry();
tools.register(calculatorTool);
tools.register(searchTool);

const agent = new ReActAgent(llm, tools, { maxSteps: 6 });
const result = await agent.run(
  "华为最新发布的旗舰手机是哪款？主要卖点是什么？",
);
console.log(result);
```

再测试多步计算：

```text
计算 (123 + 456) × 789 ÷ 12
```

由于计算器一次只能执行一个二元运算，理想轨迹应包含三次工具调用。这可以验证模型是否会使用上一步 Observation。

### 第 20 步：调试 ReAct

遇到问题时按以下顺序检查：

1. 打印发送给模型的完整提示词。
2. 打印未经处理的原始模型输出。
3. 检查 JSON 解析错误。
4. 检查工具名称是否完全一致。
5. 检查工具输入是否符合 Zod Schema。
6. 检查 Observation 是否已加入轨迹。
7. 检查是否达到最大步骤数。

## 七、阶段六：实现 Plan-and-Solve 智能体

Plan-and-Solve 把流程拆成两个阶段：

```text
Planning：复杂问题 → 完整步骤列表
Solving：根据步骤列表逐步执行
```

### 第 21 步：定义计划结构

文件：`src/agents/plan-and-solve/plan-and-solve-agent.ts`

```ts
export const planSchema = z.object({
  steps: z.array(z.string().min(1)).min(1).max(12),
});
```

限制 1 到 12 步是一个工程安全阀，避免模型生成空计划或无限细分任务。实际项目中应根据业务复杂度调整。

执行状态定义为：

```ts
export interface StepRecord {
  step: string;
  result: string;
}
```

### 第 22 步：实现规划阶段

第一次调用只负责规划，不直接回答：

```ts
const planRaw = await this.llm.generate([
  {
    role: "system",
    content: [
      "你是一名任务规划专家。",
      "把复杂问题拆分为按逻辑顺序排列、独立且可执行的步骤。",
      "只输出 JSON：{\"steps\":[\"步骤1\",\"步骤2\"]}",
      "不要直接解决问题。",
    ].join("\n"),
  },
  { role: "user", content: question },
]);

const plan = parseJson(planRaw, planSchema).steps;
```

为什么规划阶段不能顺便求解：

规划器的职责是建立全局路线。如果同时要求规划和计算，模型容易在计划中混入答案，使后续状态管理变得混乱。

### 第 23 步：逐步执行计划

```ts
const history: StepRecord[] = [];

for (const currentStep of plan) {
  const result = await this.llm.generate([
    {
      role: "system",
      content: [
        "你是任务执行专家。",
        "只完成当前步骤，不要跳过步骤。",
        "可以使用此前步骤的结果。",
      ].join("\n"),
    },
    {
      role: "user",
      content: [
        `原始问题：${question}`,
        `完整计划：${JSON.stringify(plan)}`,
        `当前步骤：${currentStep}`,
        `已完成记录：${JSON.stringify(history)}`,
      ].join("\n"),
    },
  ]);

  history.push({ step: currentStep, result });
}
```

为什么执行器同时需要完整计划和历史结果：

- 完整计划让模型知道当前步骤在全局任务中的位置。
- 历史结果保证前一步的数据能传递给后一步。
- 只提供当前步骤会失去全局目标。
- 只提供完整计划而不提供历史结果会切断步骤依赖。

### 第 24 步：生成最终答案

章节示例把最后一步结果作为答案，但更通用的工程应增加总结调用：

```ts
const answer = await this.llm.generate([
  {
    role: "system",
    content: "根据原问题和全部执行记录生成最终答案，不要遗漏关键结论。",
  },
  {
    role: "user",
    content: `原始问题：${question}\n执行记录：${JSON.stringify(history)}`,
  },
]);

return { answer, steps: plan.length };
```

这样不仅适用于数学题，也适用于报告撰写、代码设计和多来源信息整合。

### 第 25 步：运行 Plan-and-Solve 示例

使用一个依赖多步结果的问题，例如：

```text
小明有10个苹果，他又买了原来数量一半的苹果，
随后朋友送给他当前数量两倍的苹果，最后他吃掉5个。
请问还剩多少个？
```

运行时打印：

1. 完整计划。
2. 当前步骤。
3. 当前步骤结果。
4. 最终答案。

重点观察后一步是否正确使用了前一步结果，而不仅仅是观察最终数字是否正确。

### 第 26 步：理解静态计划的局限

当前计划一次生成，执行期间不能修改。如果某一步无法完成，可以进阶实现动态重规划：

1. Executor 返回步骤失败原因。
2. 保留已经成功完成的步骤。
3. 把失败原因和历史交给 Planner。
4. Planner 只生成剩余计划。
5. 设置最大重规划次数，避免反复改计划。

## 八、阶段七：实现 Reflection 智能体

Reflection 的核心流程是：

```text
生成初稿 → 反思问题 → 根据反馈优化 → 再次反思 → 完成
```

### 第 27 步：实现短期记忆

文件：`src/agents/reflection/memory.ts`

```ts
public add(record: MemoryRecord): void {
  this.records.push({ ...record });
}

public latestExecution(): string | undefined {
  return this.records.findLast(
    (record) => record.kind === "execution",
  )?.content;
}

public trajectory(): string {
  return this.records
    .map(
      (record, index) =>
        `${index + 1}. [${record.kind}]\n${record.content}`,
    )
    .join("\n\n");
}
```

如果目标 Node.js 环境不支持 `findLast`，可以使用反向 `for` 循环。

为什么需要短期记忆：

- 反思模型需要看到最近版本。
- 优化模型需要知道评审提出了什么问题。
- 完整轨迹便于调试和复盘。
- 记忆封装可以避免外部代码直接修改内部数组。

### 第 28 步：定义反思输出协议

```ts
export const reflectionSchema = z.object({
  needsImprovement: z.boolean(),
  feedback: z.string(),
});
```

示例：

```json
{
  "needsImprovement": true,
  "feedback": "当前算法对每个数字逐个试除，时间复杂度较高，建议使用埃拉托斯特尼筛法。"
}
```

为什么使用布尔字段，而不是判断文本中是否包含“无需改进”：

- 同义词可能导致漏判。
- “并非无需改进”会导致错误匹配。
- 布尔字段更容易测试。
- Zod 可以验证终止信号确实存在。

### 第 29 步：生成初稿

```ts
const draft = await this.llm.generate([
  {
    role: "system",
    content: "先完成用户任务，给出一个正确、完整、可以检查的初始方案。",
  },
  { role: "user", content: task },
]);

this.memory.add({ kind: "execution", content: draft });
```

### 第 30 步：实现反思循环

```ts
const maxIterations = this.options.maxIterations ?? 3;

for (let iteration = 1; iteration <= maxIterations; iteration += 1) {
  const current = this.memory.latestExecution();
  if (!current) throw new Error("没有可供反思的执行结果");

  const reflectionRaw = await this.llm.generate([
    {
      role: "system",
      content: [
        "你是一名严格的评审专家。",
        "从事实准确性、逻辑、遗漏、效率、边界条件和可读性方面检查结果。",
        "只输出 JSON：",
        '{"needsImprovement":true,"feedback":"具体且可执行的建议"}',
      ].join("\n"),
    },
    {
      role: "user",
      content: `原始任务：${task}\n当前结果：${current}`,
    },
  ]);

  const reflection = parseJson(reflectionRaw, reflectionSchema);
  this.memory.add({
    kind: "reflection",
    content: reflection.feedback,
  });

  if (!reflection.needsImprovement) {
    return { answer: current, steps: iteration };
  }

  const refined = await this.llm.generate([
    {
      role: "system",
      content: "根据评审反馈修改当前结果。只输出修改后的完整版本。",
    },
    {
      role: "user",
      content: [
        `原始任务：${task}`,
        `当前版本：${current}`,
        `评审反馈：${reflection.feedback}`,
        `历史轨迹：${this.memory.trajectory()}`,
      ].join("\n\n"),
    },
  ]);

  this.memory.add({ kind: "execution", content: refined });
}

const bestEffort = this.memory.latestExecution();
if (!bestEffort) throw new Error("Reflection 未生成结果");
return { answer: bestEffort, steps: maxIterations };
```

为什么设置最大迭代次数：

- 评审模型可能一直提出新的非关键建议。
- 结果质量提升会逐渐变小。
- 每轮至少增加反思和优化两次模型调用。
- Reflection 是“以成本和延迟换质量”的策略。

实际项目中，达到上限时还应该返回 `stoppedByLimit` 等元数据，避免调用方误以为结果已经完全通过评审。

### 第 31 步：运行 Reflection 示例

任务：

```text
编写一个 TypeScript 函数，返回 1 到 n 之间的全部素数，
要求说明时间复杂度并处理 n 小于 2 的情况。
```

观察轨迹：

1. 初稿是否功能正确。
2. 评审是否发现逐个试除的性能问题。
3. 优化后是否使用筛法。
4. 是否补充边界条件。
5. 评审何时认为不再需要修改。

不要只看最终代码，还要分析反馈是否具体、正确、可操作。

## 九、阶段八：编写统一运行入口

### 第 32 步：按命令行参数选择 Agent

文件：`src/index.ts`

可以把入口改造成：

```ts
import { loadConfig } from "./core/config.js";
import { OpenAiLlmClient } from "./core/openai-llm.js";
import { ToolRegistry } from "./tools/tool.js";
import { calculatorTool } from "./tools/calculator.js";
import { searchTool } from "./tools/search.js";
import { ReActAgent } from "./agents/react/react-agent.js";

const [pattern, ...questionParts] = process.argv.slice(2);
const question = questionParts.join(" ").trim();

  console.log("用法：npm run dev -- <react|plan|reflection> <问题>");
  process.exit(1);
}

const llm = new OpenAiLlmClient(loadConfig());

let result;
switch (pattern) {
  case "react": {
    const tools = new ToolRegistry();
    tools.register(calculatorTool);
    tools.register(searchTool);
    result = await new ReActAgent(llm, tools).run(question);

```

建议在入口最外层增加 `try/catch`，统一设置 `process.exitCode = 1`。不要在底层类中直接调用 `process.exit()`，否则测试和复用都会变困难。

真实模型具有以下问题：

- 输出不完全确定。
- 测试需要网络。
- 会产生费用。
- 可能受限流影响。
- 很难稳定覆盖异常分支。

因此单元测试使用预设响应的 `FakeLlmClient`。

### 第 34 步：实现假模型

新建 `tests/helpers/fake-llm.ts`：

```ts
import type { LlmClient, Message } from "../../src/core/types.js";

export class FakeLlmClient implements LlmClient {
  public readonly calls: Message[][] = [];

  public constructor(private readonly replies: string[]) {}

  public async generate(messages: Message[]): Promise<string> {
    this.calls.push(messages);
    const reply = this.replies.shift();
    if (reply === undefined) throw new Error("假模型响应已耗尽");
    return reply;

}

保存 `calls` 的原因是：测试不仅要验证最终答案，还要验证下一步提示词是否包含上一步结果。

## 十一、阶段十：比较三种范式

### 第 40 步：使用同一任务进行实验

选择一个同时包含规划、工具和质量要求的任务，例如：

```text
调查一个近期技术事件，整理三个关键事实，计算相关数据，
最后生成结构清晰且经过自查的技术摘要。
```

分别运行三种 Agent，记录：

| 指标 | ReAct | Plan-and-Solve | Reflection |
|---|---|---|---|
| 模型调用次数 |  |  |  |
| 工具调用次数 |  |  |  |
| 总耗时 |  |  |  |
| 是否动态调整 | 强 | 默认较弱 | 通过迭代调整 |
| 全局结构 | 一般 | 强 | 取决于初稿 |
| 最终质量 | 中到高 | 稳定 | 通常最高 |
| 成本 | 中 | 中 | 高 |

### 第 41 步：理解适用场景

**优先选择 ReAct：**

- 需要搜索实时信息。
- 需要调用多个外部工具。
- 无法提前确定完整执行路径。
- 希望根据环境结果动态纠错。

**优先选择 Plan-and-Solve：**

- 任务可以清楚分解。
- 步骤之间存在明确依赖。
- 强调过程结构和目标一致性。
- 例如数学题、报告结构、代码模块设计。

**优先选择 Reflection：**

- 对准确性、可靠性或代码质量要求高。
- 可以接受更高延迟和费用。
- 初稿通常有明确的评审和优化标准。
- 例如关键代码、技术报告和复杂决策分析。

### 第 42 步：尝试组合范式

真实应用通常不是三选一，可以组合为：

```text
Plan-and-Solve 制定全局计划
              ↓
ReAct 执行需要工具的具体步骤
              ↓
Reflection 审查并优化最终结果
```

这种混合设计适合研究报告、复杂客服、旅行规划和需要多个外部系统协同的任务。但必须为每一层设置调用次数和失败上限，否则成本会迅速增长。

## 十二、常见问题与排查顺序

### 1. 模型总是不返回合法 JSON

依次检查：

1. 提示词是否明确要求“只输出 JSON”。
2. 是否提供了完整示例。
3. Schema 是否与示例完全一致。
4. 是否清理了 Markdown 围栏。
5. 是否记录了原始输出。
6. 是否可以使用服务提供的原生结构化输出能力。

### 2. ReAct 重复调用同一个工具

检查 Observation 是否加入下一轮上下文，并在提示词中明确：如果结果无效，需要修改查询词或参数。还可以记录最近动作，连续重复时返回额外警告。

### 3. Plan-and-Solve 后一步没有使用前一步结果

检查执行提示词中是否同时包含：

- 原始问题。
- 完整计划。
- 当前步骤。
- 已完成步骤及结果。

### 4. Reflection 永远不结束

检查：

- 是否设置 `maxIterations`。
- 评审标准是否过于宽泛。
- 是否明确区分“必须修复的问题”和“可选建议”。
- 是否使用结构化布尔终止字段。

### 5. API 调用成本过高

可以：

- 缩短历史轨迹，只保留相关信息。
- 为计划设置最大步骤数。
- 为所有循环设置上限。
- 执行阶段使用更快、更便宜的模型。
- 关键评审阶段再使用能力更强的模型。
- 缓存重复的工具结果。

### 6. 工具数量增加到几十个

不要把所有工具描述都塞入提示词。可以先根据任务做工具检索，只给模型最相关的少量工具；也可以按领域分组，先选择工具类别，再选择具体工具。

# 学习总结

完成本项目后，需要掌握的不只是三个 Agent 类，而是智能体系统中的一组通用能力。

## 1. 普通大模型调用与智能体的区别

普通调用通常是“输入问题 → 输出答案”。智能体在模型外增加了循环、工具、环境反馈、状态和终止条件，使模型可以采取行动并根据结果继续决策。

真正的智能体能力并不完全来自模型，而是来自模型与工程控制逻辑的配合。

## 2. ReAct 的学习重点

ReAct 的核心循环是：

```text
Thought → Action → Observation
```

它最重要的价值是把模型推理和外部工具结合起来。思考决定行动，Observation 又为下一轮思考提供事实依据。

它适合探索性和实时性任务，但依赖模型的指令遵循能力，调用次数较多，也可能陷入循环。因此必须实现结构化输出、工具参数校验、错误 Observation 和最大步骤数。

## 3. Plan-and-Solve 的学习重点

Plan-and-Solve 的核心是把规划和执行分离：

```text
先拆解任务，再逐步完成
```

它的关键不只是生成步骤列表，而是执行阶段的状态管理。后续步骤必须能够看到完整计划和此前结果。

这种方式具有较强的结构性和稳定性，但静态计划对意外情况的适应能力较弱。进一步学习时应重点研究动态重规划和分层规划。

## 4. Reflection 的学习重点

Reflection 的核心循环是：

```text
执行 → 反思 → 优化
```

它通过内部评审发现事实错误、逻辑漏洞、遗漏、效率和边界条件问题，把一次性生成改造成持续优化过程。

它通常可以提高结果质量和可靠性，但每轮都增加模型调用和延迟。因此 Reflection 不是默认越多越好，而是要根据任务价值设置评审标准、迭代上限和停止条件。

## 5. 三种范式的本质区别

| 范式 | 决策方式 | 主要反馈来源 | 核心优势 | 主要代价 |
|---|---|---|---|---|
| ReAct | 每一步动态决定 | 外部工具 Observation | 环境适应、动态纠错 | 调用多、可能循环 |
| Plan-and-Solve | 先生成全局计划 | 前面步骤的执行结果 | 结构清晰、过程稳定 | 静态计划不易调整 |
| Reflection | 完成后重复审查 | 内部评审 Feedback | 提高质量和可靠性 | 成本、延迟较高 |

## 6. 工程实现中最重要的能力

本项目最终训练了以下工程能力：

1. **模型适配层**：通过 `LlmClient` 隔离具体模型服务。
2. **结构化协议**：通过 JSON 和 Zod 把模型文本转换为可靠数据。
3. **工具系统**：统一管理名称、描述、参数和执行错误。
4. **状态管理**：保存 ReAct 轨迹、计划执行记录和 Reflection 记忆。
5. **循环控制**：为每种 Agent 设置明确终止条件和最大次数。
6. **安全意识**：不执行不可信代码，不泄漏密钥，对高风险工具增加确认。
7. **可测试性**：使用假模型稳定复现模型行为，测试过程而不只测试结果。

## 7. 最终学习结论

这章最重要的学习目标不是记住某个框架的 API，而是理解：

> 一个可靠的智能体，是由模型推理能力、结构化输出、工具执行、状态记忆、错误处理和循环终止机制共同构成的。

掌握这些底层机制后，再学习 LangChain、LlamaIndex 或其他 Agent 框架时，就能理解框架替我们封装了什么、为什么这样封装，以及在标准组件不满足业务需求时应该从哪里进行定制。
